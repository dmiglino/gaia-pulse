El problema que resuelve: antes de la v3 convivían dos gramáticas de tarjeta (`rounded-2xl border-slate-200` y `rounded-xl border-slate-100 shadow-sm`) y cuatro radios (`rounded-lg/xl/2xl/full`) usados indistintamente para el mismo tipo de objeto, porque cada pantalla se escribió copiando a la anterior. Un macro convierte "¿qué radio lleva una tarjeta?" en una decisión tomada una vez. Uso: {% import 'components/ui.html' as ui %} {% call ui.card() %}...{% endcall %} {{ ui.page_header(_('Pantry'), subtitle=_('What is at home'), icon='pantry') }} {{ ui.stat(_('Weight'), '72.4', unit='kg', tone='body', icon='chart-bar') }} {{ ui.badge(_('Low'), tone='warn') }} {{ ui.btn(_('Save'), tone='primary', icon='check') }} {{ ui.avatar(current_user) }} {{ ui.tabs([{'key': 'meals', 'label': _('Meals'), 'href': '/history?tab=meals'}], current='meals', label=_('History sections')) }} Cada item de `tabs` necesita `key` (es lo que se compara contra `current`), `label` y `href`; `icon` y `count` son opcionales. Los tonos son nombres de familia de token (`brand`, `ok`, `warn`, `danger`, `info`, `food`, `move`, `body`, `stock`), no colores: cambiar el ámbar del stock bajo se hace en `app.css`, no acá ni en las 29 pantallas. Los macros que toman `tone` usan siempre los alias `-soft`/`-ink`/`-solid`, nunca un peldaño de la escala, para que ninguna familia sea un caso especial. La escala cruda (`brand-100`, `brand-700`) queda para donde hace falta un peldaño concreto: las escaleras de `hover:` y el estado activo de la nav. ── Regla de `attrs` ────────────────────────────────────────────────────────── Varios macros aceptan `attrs`, que se emite **sin escapar** para poder pasar `hx-post`, `x-on:click`, `form` o `disabled`. Por eso: NUNCA interpoles datos del request ni de la base de datos dentro de `attrs`. Es decir: `attrs='hx-post="/meals/' ~ meal.id ~ '/delete"'` está bien (un id entero), y `attrs='hx-get="/meals?q=' ~ request.query_params.q ~ '"'` es XSS — la app no tiene ninguna CSP, así que no hay segunda línea de defensa.
