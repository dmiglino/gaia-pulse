IMPORTANT CONCEPTUAL MODEL
==================================================

This is a SHARED HOUSEHOLD APP, but it must support INDIVIDUAL TRACKING.

That distinction is critical.

Shared concepts:
- household
- pantry stock
- purchases
- recipes
- household-level suggestions where relevant
- household notifications where relevant

Individual concepts:
- body metrics
- food consumption
- portions
- workouts
- preferences
- constraints
- goals
- recommendation feedback
- statistics
- activity history
- body trends

Important modeling requirement:
- A meal can be shared in time/context, but each person may eat different foods, different amounts, and different portions.
- A workout may be done by both users or by only one.
- The system must NEVER assume that if one person ate or exercised, the other one did the same.
- Every relevant event must support participant assignment and per-user details.

Examples:
- “Tonight we had dinner together: Rocío ate milanesa and 1 banana, Diego ate ravioli and ice cream.”
  -> shared time/event, different user consumption.
- “Diego rode a bike today, Rocío did not.”
  -> individual activity only.
- “We went to the gym together.”
  -> shared session with potentially different exercise details per user.

The system must compute:
- user-level statistics and suggestions,
- and household-level insights only when appropriate.

==================================================
SHARED DATA / SYNCHRONIZATION ARCHITECTURE
==================================================

The application must use a centralized shared-data architecture.

Core requirement:
- There must be a single backend and a single central database as the source of truth.
- All devices (Diego’s phone, Diego’s computer, Rocío’s phone, Rocío’s computer, etc.) must read from and write to the same backend/API and shared database.
- Do NOT design the system as multiple local databases syncing peer-to-peer between devices.
- The architecture must be server-centric and production-minded.

Expected behavior:
- If one user updates pantry stock, logs a meal, logs a workout, confirms a parsed voice/text action, or updates preferences from one device, all other devices should see that change when they refresh or reload the relevant screens.
- The system must keep household-shared data consistent across devices.
- User-specific data must also remain consistent and correctly scoped to the corresponding user.

Synchronization approach for MVP:
- Use a central PostgreSQL database and backend API as the single source of truth.
- Standard request/response synchronization is sufficient for core correctness.
- The frontend should fetch fresh data when loading screens, returning to screens, or after mutations.
- Lightweight periodic refresh / polling is acceptable in selected views where it improves UX.

Nice-to-have / architecture readiness:
- If implemented cleanly, support near-real-time updates for selected screens through Server-Sent Events (SSE) or WebSockets.
- This is optional for MVP, but the architecture should not block it in the future.

Important UX expectations:
- After a successful mutation, the initiating device must immediately reflect the saved state.
- Other devices should see the updated state with minimal friction.
- Shared screens such as pantry stock, household suggestions, notifications, and history should be designed with multi-device consistency in mind.

==================================================
NATURAL LANGUAGE + VOICE INGESTION
==================================================

This is a core differentiator and mandatory.

Implement an intelligent capture flow:

1. User enters text or records audio.
2. Audio is transcribed via an adapter.
3. Input is parsed into one or more structured intents.
4. System shows a clear “Here is what I understood” preview.
5. User may confirm, edit, or discard.
6. Only then persist data.

Requirements:
- Never auto-save parsed natural-language actions without confirmation.
- Support multiple actions in one utterance.
- Support shared and individual events.
- Must work even if LLM parsing is unavailable, using deterministic parsing fallback.

Parsing architecture:
Layer 1:
- deterministic rules
- regex
- heuristics
- entity extraction patterns
- common phrase handling

Layer 2:
- optional LLM-based parser adapter for harder cases

The parser must produce structured intermediate intents, e.g.:
- add_stock
- log_meal
- log_workout
- log_body_metric
- update_preference
- mixed_event

Support mixed inputs like:
“We bought 6 bananas and 4 bell peppers, and now Rocío is having milanesa while Diego is having ravioli.”

The interpretation preview UI must be editable before confirmation.

Voice requirements for v1:
- browser/mobile recording
- upload to backend
- transcribe through adapter
- preview/edit/confirm flow
- easy to swap STT provider later

==================================================
RECOMMENDATION / LEARNING ENGINE
==================================================

This is a major feature.

IMPORTANT:
Do NOT start with heavy machine learning unless it clearly adds value.
For MVP, implement a strong, explainable hybrid recommendation engine.

The recommendation system must learn from:
- repeated purchases
- repeated meals
- repeated recipes
- accepted/rejected suggestions
- ignored suggestions
- activity history
- explicit likes/dislikes
- impossible or context-incompatible activities
- pantry stock
- body metric trends
- workout frequency trends
- food variety patterns
- recent behavior context

Use a HYBRID recommendation strategy:

1. Hard constraint filtering
- never suggest impossible activities
- respect dislikes/restrictions
- respect dietary constraints
- respect context infeasibility

2. Rule-based wellness logic
Examples:
- low activity frequency
- low variety
- repeated sedentary periods
- pantry imbalances
- repeated lack of protein-rich options
- opportunities to use existing stock
Use prudent language and do not overclaim medically.

3. Preference scoring
Score affinities for:
- ingredients
- dishes
- meal styles
- cuisines
- activity types
- workout contexts
- time/context preferences
Use both explicit and implicit signals.

4. Controlled exploration
Do not merely repeat the same suggestions forever.
Implement a balanced exploration strategy:
- suggest adjacent foods/meals that fit known tastes
- suggest related activities/exercises that fit the user’s context
- propose feasible novelty, not random novelty

5. Explainability
Every suggestion must include:
- the suggestion text
- rationale
- what signals/data were considered
- whether it comes mostly from rules, trend detection, stock context, explicit preference, or implicit preference
- confidence/priority

Examples:
- “You have tomatoes, eggs and bell peppers in stock; a simple balanced meal could be X.”
- “Diego’s weight trend has increased over 3 weeks; consider reviewing dinner portions and adding moderate cardio if feasible.”
- “Rocío consistently rejected swimming as non-viable; do not suggest it again.”
- “You often accept biking-related suggestions, so similar low-intensity outdoor options may fit well.”

Future readiness:
Design the architecture so that later we can add:
- ranking models
- contextual bandits
- embeddings / similarity
- sequence-aware recommendations
- trend/anomaly detection
But DO NOT force that complexity into MVP.
